## 2. 帧格式

### 2.1 逐字段定义

```text
+--------+---------+----------+------------+-------------+---------+--------+
| magic  | version | msg_type | request_id | payload_len | payload | crc32  |
| 4      | 2       | 2        | 8          | 4           | N       | 4      |
+--------+---------+----------+------------+-------------+---------+--------+
  0        4         6          8            16            20        20+N
```

| 偏移 | 字节 | 字段 | 类型 | 说明 |
| --- | --- | --- | --- | --- |
| 0 | 4 | `magic` | u32 BE | 固定 `0x4D4B5031`（“MKP1”） |
| 4 | 2 | `version` | u16 BE | 固定 `1`；其他值 `unsupported_version` |
| 6 | 2 | `msg_type` | u16 BE | bit15=1 为响应；请求/响应编号见 3.1 |
| 8 | 8 | `request_id` | u64 BE | 客户端生成、连接内单调递增；响应回显 |
| 16 | 4 | `payload_len` | u32 BE | `0..8,388,608`（8 MiB） |
| 20 | N | `payload` | bytes | 报文正文 |
| 20+N | 4 | `crc32` | u32 BE | CRC32 IEEE，覆盖 `[0,20+N)`，排除自身 |

帧总长 = `24 + payload_len`；所有整数大端。

### 2.2 长度前缀、粘包与半包

1. 接收端先读 **20 字节固定头**，校验 magic、version、`payload_len ≤ 8 MiB`。
2. 按 `payload_len + 4` 读取剩余字节；不足则继续等待（半包），读满后按帧切分（粘包）。
3. 校验 CRC 后才做业务解码；CRC 失败不进入业务处理。
4. 8 MiB 帧上限与 1 MiB 单条记录上限配合：单条 1 MiB 记录（含存储头）总可装入一帧；批量请求由客户端拆分为多帧。
5. `payload_len` 超限：头可解析时返回 `request_too_large` 后关闭连接；否则直接关闭。

### 2.3 CRC 与编码原语

- CRC32 IEEE：反射多项式 `0xEDB88320`，初值 `0xFFFFFFFF`，最终异或 `0xFFFFFFFF`；测试向量 `"123456789"` → `0xCBF43926`。
- 帧 CRC 与存储记录 CRC（04 §3.3）复用同一实现但语义独立；任一失败不得由另一层补救。
- 原语：`u8/u16/u32/u64`；`str` = `u32 len` + UTF-8；`blob` = `u32 len` + 原始字节；`array<T>` = `u32 count` + 序列。
- 严格解码：字段不足、长度越界、尾随字节均 `payload_decode_error`；不压缩、不 TLV、不跳过未知字段。
- `key`/`value` 为原始 UTF-8；非法 UTF-8 返回 `invalid_utf8`，不截断。

## 3. 报文集合

### 3.1 编号与处理线程

| msg_type | 报文 | 方向 | 处理线程 | 语义 |
| --- | --- | --- | --- | --- |
| `0x0001` | CreateTopic | C→B | Main/控制面 | 创建 Topic，持久化 meta 后替换不可变快照（R30/AD-15） |
| `0x0002` | ListTopics | C→B | Main/控制面 | 列出已加载 Topic |
| `0x0003` | Produce | C→B | 分区 Storage Worker | 单分区批次，逐条结果（R23） |
| `0x0004` | Fetch | C→B | 分区 Storage Worker | 按 offset 读取；立即返回（R18） |
| `0x0005` | OffsetFetch | C→B | Group-shard Worker | 静态分配 + 已提交位点（Q-P2=A/R11） |
| `0x0006` | OffsetCommit | C→B | Group-shard Worker | 全量快照提交（S-13/R28） |
| `0x0007` | Replay | C→B | 分区 Storage Worker | 无组只读（D-06/R12） |
| `0x8001`–`0x8007` | 对应响应 | B→C | 发起请求的 IO Reactor | 以 `error_code` 开头 |

- 响应通用前缀：`error_code u16`；非 0 时紧随 `message str`（UTF-8，≤512 字节，仅诊断）；成功响应不含 message。
- **不定义**心跳、会话、join-group、成员注册、rebalance 报文（R10/Q-P2=A/B6）。

### 3.2 CreateTopic

请求：

| 字段 | 类型 | 约束 |
| --- | --- | --- |
| `topic` | str | Q-P8 `[a-z0-9_-]{1,64}` |
| `partition_count` | u32 | `1..16`（R14） |

响应：`error_code`、[`message`]、`topic`(str)、`partition_count`(u32)。
错误：`invalid_topic_name`、`invalid_partitions`、`topic_exists`、`disk_full`、`storage_io_error`。

### 3.3 ListTopics

请求：空载荷。
响应：`error_code`、[`message`]、`topic_count`(u32)、`entries[]`：`topic`(str)、`partition_count`(u32)。
说明：分区 id 为 `0..partition_count-1`，由 CLI 展开；启动时跳过的损坏 Topic 不出现在结果中（R30）。

### 3.4 Produce

请求：

| 字段 | 类型 | 约束 |
| --- | --- | --- |
| `topic` | str | 已存在 |
| `partition` | u32 | `0..partitions-1`；分区选择在客户端完成（R22/Q-P13） |
| `entry_count` | u32 | `1..1024` |
| `entries[]` | array | 每项见下 |

每项：`flags`(u16，bit0=`KEY_PRESENT`，其余位必须 0)、`key_len`(u32)、`key`(bytes)、`value_len`(u32)、`value`(bytes)。
- key 缺失：`flags.bit0=0` 且 `key_len=0`；空字符串 key：`flags.bit0=1` 且 `key_len=0`（R14/R22）。
- value 必须存在；空字符串合法（`value_len=0`）。

响应：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `status` | u8 | `0=全部追加`、`1=部分追加`、`2=无条目追加` |
| `result_count` | u32 | 等于 `entry_count`（请求级失败时为 0） |
| `results[]` | array | `index`(u32)、`status`(u8：0=appended/1=failed/2=not_attempted)、`error_code`(u16)、`offset`(u64) |

- 结果顺序与请求一致；`index` 即失败条目的定位标识（R23）。
- 成功条目 `offset` 有效且连续递增；失败/未尝试条目 `offset=0`。
- **AD-14**：同分区首个失败后，后续条目 `status=2`、`error_code=partition_blocked`；其他分区是独立请求，不受影响。
- 请求级错误（如 `topic_not_found`/`invalid_partition`）：`status=2`、`result_count=0`。

### 3.5 Fetch

请求：`topic`(str)、`partition`(u32)、`offset`(u64)、`max_bytes`(u32；0=默认 1 MiB，上限 4 MiB)。
响应：`error_code`、[`message`]、`topic`(str)、`partition`(u32)、`log_end_offset`(u64)、`record_count`(u32)、`records[]`。
每条记录：`offset`(u64)、`flags`(u16)、`key_len`(u32)、`key`、`value_len`(u32)、`value`。

- `offset == log_end_offset`：成功、0 条记录（合法“从末尾跟随”）。
- `offset > log_end_offset`：`offset_out_of_range`（Q-P7）。
- 无删除（R25），最早 offset 恒为 0，无需 earliest 查询。
- 只返回完整记录；至少返回 1 条能容纳的记录；上限 4 MiB 或 500 条。
- **立即返回，不注册等待者、不做长轮询**（见第 7 节）。

### 3.6 OffsetFetch（含静态分配）

请求：`group`(str，R31)、`topic`(str)、`consumer_index`(u32)、`consumer_count`(u32，`1..16`)。
响应：`error_code`、[`message`]、`assigned_count`(u32)、`assigned_partitions[]`(u32)、`entry_count`(u32)、`entries[]`。

每项：`partition`(u32)、`has_committed`(u8)、`committed_offset`(u64；`has_committed=0` 时忽略)。

- 分配纯函数：`partition % consumer_count == consumer_index`；无成员表、无心跳、无分配结果持久化（Q-P2=A）。
- `entry_count == assigned_count`，按 partition 升序。
- 无位点（新 group/新分区）→ `has_committed=0`；双槽均损坏 → 同样返回 `has_committed=0`，Broker 侧 stderr 告警（R28）。
- 错误：`invalid_group_name`、`invalid_consumer_slot`、`topic_not_found`。

### 3.7 OffsetCommit

请求：`group`(str)、`topic`(str)、`entry_count`(u32，`0..16`)、`entries[]`：`partition`(u32)、`committed_offset`(u64)。
响应：`error_code`、[`message`]、`applied_count`(u32)。

- 语义：`committed_offset` = 下一条待消费 offset；`< committed_offset` 视为已处理（R11/R28）。
- 全量快照：Broker 将请求条目合并到该 `(group, topic)` 的内存位点表（未出现在请求中的分区保留原值），再写完整快照；任一校验失败则整体不应用（S-13）。
- 不回退：同一分区新值小于现有值时保留现有值（取 max，04 §6.3）。
- 分区范围由客户端按分配结果保证；Broker 只校验 `0..partition_count-1`，不校验槽位归属（无成员状态，Q-P2=A）。
- 写入页缓存并 rename 后返回成功，不 fsync；写失败返回 `disk_full`/`storage_io_error`，客户端按 R8 退避重试、不退出。
- 错误：`invalid_group_name`、`invalid_consumer_slot`、`topic_not_found`、`invalid_partition`。

### 3.8 Replay（无组只读）

请求：`topic`(str)、`partition`(u32)、`offset`(u64)、`count`(u32；0=读到末尾)。
响应：同 Fetch 的成功响应结构（含 `log_end_offset` 与 `records[]`）。

- 不含 group 字段；不经过分配/位点路径；不提交、不改变任何 group 状态（D-06/R12）。
- `offset > log_end_offset` → `offset_out_of_range`；`count` 超过可读条数 → 返回现有条数并成功。
- 单响应上限 4 MiB/500 条；客户端以 `offset + 返回条数` 续拉直到 count/末尾。

## 4. 批量逐条结果与 1 MiB 边界

### 4.1 结果编码

| status | 名称 | offset | error_code | 客户端动作 |
| --- | --- | --- | --- | --- |
| 0 | appended | 有效 | 0 | 记录成功 offset；输出逐条结果 |
| 1 | failed | 0 | 失败码 | 可重试码 → 退避重试；校验码 → 不重试 |
| 2 | not_attempted | 0 | `partition_blocked` | 待失败条目成功后按原顺序重发 |

- 逐条结果即 R23 的“成功含 offset、失败含原因或定位标识”；`index` 为定位标识。
- 同分区后续条目不越过失败条目（AD-14/R2/R24）；其他分区独立。

### 4.2 与 04 记录格式的边界

| 04 字段 | 05 来源 | 说明 |
| --- | --- | --- |
| `flags.KEY_PRESENT` | Produce 条目 `flags` bit0 | 1:1 映射；其他位必须 0 |
| `key_len`/`value_len` | Produce 条目同名字段 | 协议只传原始字节；存储记录头由 Broker 构造 |
| `record_size` | `24 + key_len + value_len` | ≤ 1 MiB（R17/S-09） |
| `offset` | Broker 分配 | 协议不携带写入 offset；只出现在响应 |
| 时间戳 | 无 | MVP 不存（S-08） |

- **1 MiB 的两次权威校验**：Broker 协议解码后逐条校验；Storage Worker 追加前再校验（04 §3.5）。协议帧头、批量头、逐条 flags/长度字段**不计入** `record_size`。
- 超限条目：`message_too_large`，不截断、不写入；同分区后续 `not_attempted`（AD-14）。
- 客户端前置校验仅为快速失败；权威校验在 Broker。

### 4.3 客户端重试映射

| 情况 | 逐条结果/事件 | 重试 | 退出码 |
| --- | --- | --- | --- |
| 全部成功 | 逐条 `ok` | — | 0 |
| 部分失败、存在可重试码 | 失败条目重试，分区阻塞；其他分区继续 | R3/R24 | 成功 0；耗尽 4 |
| 仅校验类失败 | 逐条错误 + `produce_summary` | 不重试 | 3 |
| 某分区重试耗尽 | 逐条错误 + 按分区成功 offset 汇总（R29） | 停止该分区 | 4 |

- `produce_summary` 由 CLI 输出（Q-P12），不属于线上报文；`exit_reason` 取 `retry_exhausted`/`validation_error`。

## 6. 跟随等待策略

1. **Fetch 立即返回**：offset 等于末尾时返回 `ok + 0 条 + log_end_offset`；Broker 不注册等待者、不阻塞 Storage Worker。
2. **客户端轮询**：Consumer 对自己分配的全部分区各发一个 Fetch；若本周期全部为空，等待 **100ms** 后重发；有数据则立即继续。无抖动。
3. `--exit-at-end`：首次“全部分区为空且 offset=末尾”即补一次最终提交（Q-P6，最多等 2s），退出 0（R18）。
4. 默认跟随：持续轮询直至 Ctrl+C；自动提交定时器（默认 5s，Q-P4）在 Client Reactor 独立触发，不受轮询影响（R6）。
5. **不做 Broker 侧长轮询**：03 只为客户端 Reactor 定义了定时器（AD-06），Broker 无定时器/等待队列线程；客户端轮询避免新增 Broker 线程、避免 Storage Worker 被空闲等待占用（AD-04/RK-11）。
6. Replay 不使用跟随：`count` 读到指定条数/末尾即结束（R12）。

## 7. 与 03 网络模型的落点

### 7.1 请求线程流转

| 阶段 | 执行者 | 行为 |
| --- | --- | --- |
| 连接建立 | Main Reactor | accept；按轮询/负载分配到某个 IO Reactor |
| 读帧 | IO Reactor（LT + 非阻塞） | 读到 EAGAIN；半包留缓冲；校验帧头/CRC；M2 解码 |
| 控制面 | Main | CreateTopic/ListTopics 作为控制面任务；M5 更新快照、M4 写 meta |
| 分区读写 | 分区所属 Storage Worker | 经有界 MPSC 队列；磁盘预检、offset 分配、追加/读取；M4 |
| 组请求 | Group-shard Storage Worker（`hash(group) % M`） | OffsetFetch/OffsetCommit；M6 纯函数 + M4 位点文件 |
| 响应 | 发起请求的 IO Reactor | Storage Worker 完成事件 + eventfd；按 `request_id` 编码回送 |

- IO 线程不做磁盘 I/O；热路径不写日志（03 §5.4）。
- 响应可能乱序（不同分区/不同 worker 完成时间不同）；客户端按 `request_id` 关联，不假设顺序。
- 同一分区同一时刻客户端只允许 1 个 Produce 在途（R2）；Broker 侧由单一 Storage Worker 串行追加（AD-05/AD-13）。

### 7.2 背压与边界

| 机制 | 规则 |
| --- | --- |
| 每连接在途请求 | ≤ 64；超过移除 `EPOLLIN`，降到低水位恢复 |
| Storage Worker 队列 | 有界 MPSC；高水位 4096、低水位 1024（建议值，实现可调） |
| 读缓冲 | 只按 `payload_len` 预留；超 8 MiB 拒绝，不无限增长 |
| 写缓冲 | 高水位暂停产生新响应；连接关闭后迟到完成事件按代际 id 安全丢弃 |
| 慢消费者 | 客户端 stdout 阻塞即自然背压（03 RK-12）；Broker 不感知 |

### 7.3 连接与错误

- 帧解码失败、版本不支持、请求过大：返回错误后关闭连接；客户端按错误类别决定重试/退出。
- TCP 断开：Producer 按 R3 重试；Consumer 按 R8 持续重连，不主动退出。
- 不设心跳报文（R10/Q-P2=A）；连接存活由 TCP 与请求/响应活动体现。

## 8. 与 04 的一致性核对

| 04 要求 | 05 落点 | 结论 |
| --- | --- | --- |
| Topic/分区路由、单分区串行 | Produce/Fetch/Replay 只含一个 partition；分区选择在客户端 | 一致 |
| key 缺失/空字符串与 `KEY_PRESENT` | Produce 条目 `flags.bit0` + `key_len` | 一致 |
| `record_size ≤ 1 MiB` | 协议解码校验 + 追加前校验；协议开销不计入 | 一致（R17/S-09） |
| offset 由 Broker 分配 | Produce 响应回传 offset；请求不携带写入 offset | 一致（R27） |
| 逐条结果、首失败停止 | `results[]` status 0/1/2；AD-14 → `partition_blocked` | 一致（R23/R24） |
| 磁盘满拒写 | `disk_full`；不 ack、后续 `not_attempted` | 一致（R16） |
| 位点双槽/回退 | OffsetFetch `has_committed`；OffsetCommit 全量快照 | 一致（R28） |
| 损坏 Topic 跳过 | `topic_not_found`；同名创建 `topic_exists` | 一致（R30） |
| 分区不可用（基址断链/封存损坏） | `storage_unavailable` | 一致（D-04-6） |
| Replay 只读、无副作用 | 独立报文、无 group 字段、不提交 | 一致（R12/D-06） |
| 1 MiB 之外无其他消息上限 | 帧 8 MiB、批量 1024 条、响应 4 MiB/500 条 | 一致（B5 由 05 定稿） |
