| 术语 | 含义 |
| --- | --- |

## 2. 数据目录总览

### 2.1 目录树

与 `03.整体架构设计.md` 第 7.2 节一致；本文件把文件级布局落细。

```text
<data-dir>/                                  # 默认 ./data
├── meta/
│   ├── <topic>.meta                         # R30：每 Topic 一个元数据文件
│   └── <topic>.meta.tmp                     # 原子写临时文件；启动时忽略
├── topics/
│   └── <topic>/                             # Topic 名已校验 [a-z0-9_-]{1,64}
│       └── <partition>/                     # 十进制 0..15
│           ├── 00000000000000000000.log     # 分段：base offset 20 位十进制
│           ├── 00000000000000000000.index   # 稀疏索引；派生数据
│           ├── 00000000000000012345.log
│           └── 00000000000000012345.index
└── groups/
    └── <group>/                             # Group 名已校验 [a-z0-9_-]{1,64}
        └── <topic>/
            ├── offsets.a                    # 完整位点快照槽 A
            ├── offsets.b                    # 完整位点快照槽 B
            └── offsets.tmp                  # 写入中间文件；启动时忽略
```

**文件职责**

| 路径 | 内容 | 可靠性 |
| --- | --- | --- |
| `meta/<topic>.meta` | Topic 名称 + 分区数 | 原子写；带 CRC；单文件损坏只跳过该 Topic（R30） |
| `topics/<topic>/<partition>/<base>.log` | 顺序追加的消息记录 | 页缓存持久化；尾部残缺按 R7 截断 |
| `topics/<topic>/<partition>/<base>.index` | 稀疏 offset → 文件位置索引 | 派生数据；可重建；不单独保证 |
| `groups/<group>/<topic>/offsets.a / offsets.b` | 该 group/topic 全部分区的已提交位点 | 双槽快照；CRC；回退上一完整槽（R28） |
| `*.tmp` | 原子写中间态 | 启动忽略；不删除、不作为有效数据 |

### 2.2 路径安全与名称校验

- Topic 名：Q-P8 `[a-z0-9_-]{1,64}`；由 M5 Topic 控制面校验，M4 路径构造器再次拒绝非法名。
- Group 名：R31 `[a-z0-9_-]{1,64}`；与 Topic 名完全一致。
- **R31 Group 名校验的执行位置**：
  1. **M7.3 Consumer CLI**：启动时先做格式校验（快速失败）。
  2. **M5 Broker Core / M6 组逻辑（运行于 Group-shard Storage Worker）**：创建 `<data-dir>/groups/<group>/<topic>/` 前做**权威校验**；非法名称直接拒绝，不创建任何目录。
  3. **M4 存储层路径构造器**：只接受已校验的 `GroupName` 类型或再次校验；禁止把原始字符串直接拼入路径。
- 分区号必须是十进制 `0..partitions-1`；分区数 1–16（R14）。
- 任何名称校验失败都不得创建目录、不得写入文件；错误返回给客户端（错误码属 05）。

### 2.3 目录生命周期

- Topic 创建：创建分区目录与初始空分段（base=0）→ 原子写 `<topic>.meta` → 替换 M5 不可变快照（AD-15）。
- Topic 元数据存在但日志目录缺失：启动时跳过该 Topic 并告警（告警含 Topic 名与缺失路径），不伪造空日志。
- 无元数据的孤儿日志目录：启动时忽略并告警；不删除。
- 位点目录按 `(group, topic)` 创建；Group/Topic 名已校验。

## 3. 消息记录格式

### 3.1 字节序

所有整数字段一律**大端（network byte order）**。key/value 是原始 UTF-8 字节，不按字节序处理。

### 3.2 逐字段定义

| 偏移 | 字节数 | 字段 | 类型 | 含义 |
| --- | --- | --- | --- | --- |
| 0 | 4 | `total_len` | uint32 BE | 本字段之后的字节数，含 CRC、头、key、value |
| 4 | 4 | `crc32` | uint32 BE | CRC32 IEEE；覆盖范围见 3.3 |
| 8 | 4 | `magic` | uint32 BE | 固定 `0x4D4B4146`（ASCII “MKAF”） |
| 12 | 2 | `version` | uint16 BE | 记录格式版本；MVP = 1 |
| 14 | 2 | `flags` | uint16 BE | bit0 = `KEY_PRESENT`；其余位 MVP 必须为 0 |
| 16 | 4 | `key_len` | uint32 BE | key 的 UTF-8 字节数；可为 0 |
| 20 | 4 | `value_len` | uint32 BE | value 的 UTF-8 字节数；可为 0 |
| 24 | `key_len` | `key` | UTF-8 bytes | 原始 UTF-8，无 NUL 终止符 |
| 24 + `key_len` | `value_len` | `value` | UTF-8 bytes | 原始 UTF-8，无 NUL 终止符 |

**自洽关系**

```text
total_len   = 20 + key_len + value_len
record_size = 4 + total_len
record_size = 24 + key_len + value_len
```

最小记录为 24 字节（空 key + 空 value）。MVP 不存时间戳（S-08）。

### 3.3 total_len 与 CRC 的字节范围

```text
字节偏移:  0        4        8                                              record_size
          +--------+--------+------------------------------------------------+
          |total_len| crc32 | magic | version | flags | key_len | value_len | key | value |
          +--------+--------+------------------------------------------------+
          |<- 4 -->|<- 4 -->|                                                  |
          |<----------------- CRC 覆盖 [0,4) ∪ [8, record_size) -------------->|
          |<----------------- total_len = record_size - 4 -------------------->|
```

- **CRC32 IEEE**：反射多项式 `0xEDB88320`，初值 `0xFFFFFFFF`，最终异或 `0xFFFFFFFF`；标准测试向量 `"123456789"` → `0xCBF43926`。
- CRC 覆盖 `total_len`（4 字节）和 `magic` 到 `value` 的全部字节；**排除 CRC 字段自身** `[4,8)`。
- 长度字段被破坏时，CRC 会失败；配合长度范围检查与自洽检查，避免把错误长度当作合法边界。
- `crc32` 字段自身不参与计算；CRC 计算跨越非连续区间 `[0,4)` 与 `[8,record_size)`。

### 3.4 半条记录识别

恢复/读取时按以下顺序判断：

1. 剩余不足 4 字节 → 半条头部；尾部截断。
2. 读取 `total_len`；若 `< 20` → 非法长度。
3. 计算 `record_size = 4 + total_len`；若 `record_size > 1 MiB` → 非法（超过 R17/S-09）。
4. 若当前位置 + `record_size` > 文件末尾 → 半条记录；尾部截断。
5. 读取完整记录，检查：
   - `magic == 0x4D4B4146`
   - `version == 1`
   - `flags` 保留位为 0
   - `total_len == 20 + key_len + value_len`
6. 计算 CRC32 并比对；失败 → 从该记录起点截断。
7. 全部通过 → 记录有效，继续下一条。

### 3.5 1 MiB 上限的两次校验（R17/S-09）

| 校验点 | 执行者 | 时机 | 行为 |
| --- | --- | --- | --- |
| 协议请求校验 | M5 Broker Core（协议解码后） | 请求进入 Broker 时 | 逐条检查 `record_size = 24 + key_len + value_len`；> 1 MiB 立即拒绝该条，不进入存储 |
| 追加前校验 | Storage Worker（M4 调用方） | 路由到分区、分配 offset 之前 | 再次计算 `record_size`；> 1 MiB 拒绝；不写记录、不分配 offset、不 ack |

- 两次校验都必须拒绝，**不截断**。
- 协议帧头、批量请求头不计入单条 1 MiB；R17 已回写口径澄清。
- 客户端可做前置校验以快速失败，但权威校验在 Broker 两处。

### 3.6 key/value 编码与 KEY_PRESENT

- `key`、`value` 都是原始 UTF-8 字节，无 NUL 终止符，长度由 `key_len`/`value_len` 指定（R19/Q-P14）。
- `flags.bit0 = KEY_PRESENT`：
  - `1`：客户端提供了 key；`key_len = 0` 表示空字符串 key，仍参与哈希分区（R14/R22）。
  - `0`：key 缺失/null；`key_len` 必须为 0，分区选择走轮询。
- `value` 必须存在；空字符串时 `value_len = 0` 合法。
- 写入前校验 UTF-8 合法；非法 UTF-8 拒绝，不写入、不截断。
- 不支持二进制/base64（P1）；未来支持需提升 `version` 或引入明确的编码标志。
- 保留 flags/version 位不得随意使用；未知 version 视为损坏/不支持，拒绝该记录。

## 4. 分段文件与索引

### 4.1 命名

```text
<data-dir>/topics/<topic>/<partition>/<base_offset:020d>.log
<data-dir>/topics/<topic>/<partition>/<base_offset:020d>.index
```

- `base_offset` 是分段第一条记录的 offset，20 位十进制（64 位 offset 最大宽度），字典序 = 数值序。
- 不使用自增序号或时间戳命名；base offset 是分段身份的一部分。
- 分段文件无单独文件头；由完整记录顺序拼接。
- 索引文件与分段文件一一对应；索引缺失/损坏可从日志重建。

### 4.2 滚动触发条件

1. 追加前计算 `new_size = active_size + record_size`。
2. 若 active segment 非空且 `new_size > segment_bytes` → 封存 active，创建新分段，`base_offset = next_offset`，并写入新分段首条记录的索引检查点。
3. `--segment-bytes` 下限为 **2 MiB**；单条记录上限 1 MiB，因此正常配置下 `record_size < segment_bytes`。若配置/校验异常导致 `record_size > segment_bytes`，**拒绝该条**，不创建超大分段（S-12）。
4. 同一分区的滚动、封存、创建新分段均由该分区所属 Storage Worker 串行执行。

### 4.3 分段大小（B5）

- 默认 **256 MiB**；`--segment-bytes` 可配置，下限 2 MiB。
- 依据：100B 记录约可容纳 2.56M 条；100k 条/秒下约 25.6s 滚动一次，避免数秒一次滚动，同时控制恢复扫描与文件数量。
- 分段大小不改变正确性，只影响滚动频率、恢复扫描时间与文件数量。

### 4.4 稀疏索引

**索引条目**（固定 12 字节，无文件头）：

```text
offset   : uint64 BE   # 记录逻辑 offset
position : uint32 BE   # 记录在分段文件内的字节偏移
```

- 分段默认 256 MiB < 4 GiB，`position` 用 uint32 足够；若未来允许更大分段，必须升级索引格式与版本。
- 索引文件长度必须是 12 的整数倍；条目 offset 必须严格递增、position 必须在文件范围内；否则重建。
- **索引是派生数据，不是正确性来源**：崩溃后从日志重建；不单独做可靠性保证（S-04）。

**检查点写入时机**

- 分段第一条记录在 position 0 处必须有检查点。
- 维护 `last_checkpoint_position`；每追加一条记录，若其起始位置 `P` 满足 `P - last_checkpoint_position >= 4096`，为该记录追加索引条目 `(offset, P)`，并更新 `last_checkpoint_position = P`。
- 索引写在数据记录追加之后；索引写失败不影响 ack，重建时补齐。
- 索引条目只指向记录起点，不记录长度；读取时仍按记录头解析。

**重建步骤**

1. 以只读方式顺序扫描分段，按第 3.4 节校验记录。
2. 第一条有效记录写入 `(offset, position=0)`。
3. 按 4 KiB 间隔为后续记录追加检查点。
4. 将新索引写入 `<base>.index.tmp`，再 rename 覆盖 `<base>.index`。
5. 若扫描中途失败：保留旧索引或标记索引缺失；读取走无索引线性扫描；不阻塞 Broker 启动。
6. 启动时至少重建 **active segment** 的索引；封存分段索引按需重建或可选全量校验。

### 4.5 按 offset 定位

1. 在分区段列表中二分查找 `base_offset <= target` 的最大分段。
2. 读取该段索引，二分查找最后一个 `offset <= target` 的检查点。
3. 从检查点 `position` 顺序扫描记录，直到 `record.offset == target` 或越过 target。
4. 找不到 → 返回 `offset_out_of_range`（错误码属 05）。
5. 索引缺失/损坏 → 从分段起点线性扫描，并重建索引。

**复杂度**：有索引 O(log 段数 + log 索引条目 + 检查点间隔内记录数)；无索引 O(段内记录数)。4 KiB 检查点间隔在 100B 记录下平均约 40 条记录。

### 4.6 封存分段只读

- 封存分段不可追加、不可截断、不可修改（S-10/S-11）。
- 恢复只允许截断 **active segment**；封存分段仅在读取或可选全量校验时扫描。
- 封存段损坏时不得修改文件；按第 8 节边界用例处理。

## 5. offset 与保序

### 5.1 分配规则（R2/R27）

- offset 是分区内单调递增的逻辑序号，从 0 开始；与物理字节位置、分段名解耦。
- 由该分区唯一所属的 Storage Worker 在追加前分配：
  - 成功追加一条 → `next_offset += 1`。
  - 失败条目不分配 offset、不写记录、不占用 offset。
- 同一分区同一时刻只有一个追加任务；跨分区可并行。
- 同一批内同分区条目按输入顺序处理；某条失败后，该分区后续条目不再追加（AD-14），其他分区继续。

### 5.2 重启重建 `next_offset` 的完整步骤

> 恢复只截断 active segment；封存分段只读（S-11）。

1. 枚举 `<partition>/` 下所有 `*.log`，按 `base_offset` 升序排序；忽略 `*.tmp`。
2. 校验 base offset 链：
   - 首段 base 必须为 0；首段缺失或无 base=0 分段即视为基址断链（R27：offset 从 0 开始且不删除）。
   - 后一段 base 应等于前一段最后一个记录 offset + 1。
   - 若链不连续 → 该分区标记为不可用并告警，不修改任何分段；停止后续恢复（见边界表）。
3. 若没有任何分段：`next_offset = 0`；创建 base=0 的空 active 分段。
4. 取最后一个分段为 active：
   1. 从起点（或可信索引检查点）顺序读取，按第 3.4 节校验。
   2. 记录最后一条有效记录的 offset 与结束位置。
   3. 遇到第一条无效/不完整记录 → 停止；`ftruncate` active 到最后有效记录结束位置（没有有效记录则截断到 0）。
   4. `next_offset = 最后有效 offset + 1`；若 active 没有有效记录，`next_offset = active.base_offset`。
5. 封存分段：只读扫描其尾部/索引以确认最后一个 offset 与 active.base_offset 的衔接；不修改。
6. 重建 active 索引；封存索引按需重建。
7. 分区恢复完成后，M5 将分区标记为可服务；acceptor 在所有分区恢复完成后才启动（AD-16）。

**说明**

- 正常崩溃只会留下 active segment 的残缺尾部；封存段由滚动逻辑保证完整。
- 全量校验仅作为独立测试开关/编译期选项，**MVP 不新增 Broker CLI 参数**（D-04-3，避免改动 03 的 B4 契约）；会只读扫描封存段，发现损坏时不修改，按边界表标记分区不可用并告警。
- 空 active 分段（0 字节）合法：`next_offset = base_offset`，文件保留。

## 6. 位点文件（R28）

### 6.1 位置

```text
<data-dir>/groups/<group>/<topic>/offsets.a
<data-dir>/groups/<group>/<topic>/offsets.b
<data-dir>/groups/<group>/<topic>/offsets.tmp
```

- 每个 `(group, topic)` 两个完整快照槽；快照包含该组在该 Topic 下所有分区的已提交位点。
- Group 名按 R31 在创建目录前校验（见 2.2）。
- `committed_offset` = 下一条待消费 offset；`offset < committed_offset` 视为已处理。

### 6.2 格式

```text
Header:
  magic              uint32 BE   # "MKOF" = 0x4D4B4F46
  version            uint16 BE   # 1
  header_size        uint16 BE   # 24
  generation         uint64 BE   # 单调递增
  entry_count        uint32 BE
  reserved           uint32 BE   # 0

Entries (entry_count 个，每个 12 字节，按 partition 升序、唯一):
  partition          uint32 BE   # 0..15
  committed_offset   uint64 BE   # 下一条待消费 offset

Footer:
  crc32              uint32 BE   # CRC32 IEEE，覆盖 Header + Entries，不含 Footer
```

- 文件大小 = 24 + 12 × `entry_count` + 4。
- `entry_count = 0` 合法。
- 所有整数大端；CRC 算法与记录格式一致（CRC32 IEEE）。
- 校验：magic、version、header_size=24、entry_count、文件长度、CRC、partition 范围与唯一性。

### 6.3 写入时机

1. **自动提交**：客户端每 `--auto-commit-interval`（默认 5s，Q-P4）提交“已处理位点”；Group-shard Storage Worker 更新内存位点后写全量快照。
2. **正常退出补提交**：Consumer 在 Ctrl+C / `--exit-at-end` 前补一次提交（Q-P6）；走同一写入路径。
3. **成功时点**：快照写入页缓存并完成 rename 后返回成功；**不 fsync**（R28/R1）。
4. **失败**：返回错误；客户端按 R8 退避重试并告警，不退出。
5. **粒度**：每次提交写该 `(group, topic)` 全量快照（S-13）；默认 5s 间隔下写放大可接受。
6. **不回退**：同一分区的新提交值若小于现有已提交位点，保留现有值（取 max）；避免重试或乱序提交扩大重复窗口（R11/R28）。

### 6.4 双槽切换流程

- 两个槽 `offsets.a` / `offsets.b` 各保存一份完整快照，`generation` 递增。
- 初始：两槽可都不存在；首次提交写 `offsets.a`，generation = 1。
- 后续提交：
  1. 序列化新快照到 `offsets.tmp`（同目录，保证 rename 不跨文件系统）。
  2. 选择 generation 较旧（或不存在）的槽作为目标。
  3. `rename(offsets.tmp, 目标槽)`；另一个槽保持上一完整快照。
  4. 新槽 generation 最大；旧槽作为“上一份完整位点”。
- 历史消息分段不受影响；只覆盖较旧的位点快照槽（S-10）。

### 6.5 四种崩溃时序

| 崩溃时序 | 磁盘状态 | 恢复行为 | 影响 |
| --- | --- | --- | --- |
| tmp 写入中崩溃 | `offsets.tmp` 不完整；两个正式槽未变 | 忽略 tmp；读取两个正式槽，选最大有效 generation | 最近一次提交丢失；重复窗口从上次快照起；客户端可重试 |
| tmp 写完但未 rename | tmp 完整但未命名；正式槽未变 | 忽略 tmp；使用旧最新有效槽 | 本次提交未生效；重复窗口从旧快照起 |
| rename 完成后，旧槽仍为旧 generation | 新槽完整且 generation 最大；旧槽为上一快照 | 选新槽；旧槽保留作回退 | 本次提交生效；上一快照仍可用于新槽损坏时回退 |
| 两槽均损坏 | 两槽 CRC/格式均失败 | 视为无已提交位点；stderr 告警；Broker 启动 | 该 group 下次按 `--from`（R11）开始；可能重复/从头消费，但不丢消息 |

- 若 rename 后新槽内容损坏：恢复回退到旧槽；重复窗口扩大。
- 回退造成的重复仍满足至少一次；正常路径重复窗口 ≤ 一个自动提交间隔（默认 5s）。
- V2 验收需区分“正常崩溃”和“位点损坏/回退”两种场景。

## 7. Topic 元数据（R30）

### 7.1 位置

```text
<data-dir>/meta/<topic>.meta
<data-dir>/meta/<topic>.meta.tmp
```

- 每 Topic 一个文件；单文件损坏只影响该 Topic。
- Topic 名按 Q-P8 校验；文件名与内部 name 必须一致。

### 7.2 格式

```text
magic            uint32 BE   # "MKTM" = 0x4D4B544D
version          uint16 BE   # 1
flags            uint16 BE   # 0
partition_count  uint32 BE   # 1..16
name_len         uint32 BE
name             UTF-8 bytes # Topic 名
crc32            uint32 BE   # CRC32 IEEE，覆盖以上所有字节（不含 crc 自身）
```

- 所有整数大端。
- 校验：magic、version、flags=0、`1 <= partition_count <= 16`、name 合法、name_len/文件长度匹配、CRC 正确。
- 元数据只记录名称与分区数；不记录消息或位点。

### 7.3 原子写

1. 在 `meta/` 下创建 `<topic>.meta.tmp`。
2. 写入完整内容并关闭（页缓存；不要求 fsync）。
3. 同目录 `rename` 到 `<topic>.meta`。
4. 启动忽略残留 `*.tmp`；不删除。

### 7.4 启动扫描重建

1. 枚举 `meta/*.meta`，忽略 `*.tmp`。
2. 逐个校验格式与 CRC。
3. 有效：加入 M5 Topic 候选列表。
4. 损坏/非法：**跳过该 Topic + stderr 告警**；告警必须包含 **Topic 名 + 文件路径/缺失日志路径**；其他 Topic 继续；不阻止 Broker 启动（R30/S-14）。
5. 文件名与内部 name 不一致、分区数非法：视为损坏，跳过并告警。
6. 不自动删除、不自动修复损坏文件。
7. 损坏 Topic 的目录与文件保留原位；同名 `topic create` 返回 `topic_exists`，不得覆盖或复用损坏目录（S-10/S-14）。
8. 若元数据有效但某分区日志目录/分段缺失：跳过该 Topic + 告警（含缺失路径），不伪造空日志（S-14）。

### 7.5 与 AD-15 不可变快照的并发可见性

1. Topic 创建由 M5 控制面串行处理：
   1. 创建 `<topic>/` 与各分区目录、初始空分段（base=0）。
   2. 原子写 `<topic>.meta`。
   3. 构造新的不可变 Topic 快照（copy-on-write），原子替换当前快照。
2. 快照替换前，新 Topic 对 Producer/Consumer 不可见；已有请求继续使用旧快照，不会看到半成品。
3. 若崩溃在步骤 1 与 2 之间：留下无元数据的日志目录；启动忽略并告警，不对外提供 Topic。
4. 若元数据存在但日志缺失：见 7.4 第 7 条；跳过并告警。
5. 创建完成后，新 Topic 立即可见；分区数不可变（R14）。

## 8. 恢复流程

### 8.1 启动到 acceptor 就绪（AD-16）

1. 解析参数，确认 `<data-dir>` 可读写；不存在则创建。
2. 扫描 `meta/*.meta`，校验并加载有效 Topic；损坏 Topic 跳过 + 告警（含 Topic 名/路径）。
3. 对每个 Topic/Partition：
   1. 枚举分段，按 base offset 排序，校验 base 链。
   2. 按第 5.2 节重建 active segment 的 `next_offset`；只截断 active，不修改封存段。
   3. 重建 active 索引；封存索引按需重建。
   4. 单个分区恢复失败（基址断链/封存段损坏/首条记录非法）时，**仅该分区**标记不可用，后续对该分区的写/读返回 `storage_unavailable`（05 定义）；同 Topic 其他分区与其他 Topic 正常服务，Broker 照常 ready（D-04-6）。
4. 扫描 `groups/*/*/offsets.a` 与 `offsets.b`，校验并选择最大有效 generation；损坏回退（R28）。
5. 初始化磁盘空间状态：查询可用空间；低于默认 256 MiB 阈值 → 低空间状态（读可服务，写拒绝）。
6. 启动 Storage Worker、IO Reactor、Logger 线程。
7. 启动 acceptor，输出 ready；**此前不接收客户端请求**。

### 8.2 追加调用链（无 fsync）

```text
协议请求校验（M5；record_size ≤ 1 MiB）
  → 路由到分区所属 Storage Worker
  → 磁盘空间预检（R16；默认 256 MiB 阈值）
  → 分配 next_offset（R27）
  → 构造记录（total_len/CRC32/magic/version/flags/key/value）
  → 追加到 active segment（页缓存）
  → 追加成功返回（记录完整进入页缓存）
  → 该条成功结果 + offset
  → IO 线程编码响应（客户端收到 ack）
```

- **fsync 不在链路**（R1）。
- 预检失败：不分配 offset、不写、不 ack。
- 预检通过但写入失败（RK-06）：不 ack；标记低空间状态；恢复时截断 active 尾部；读路径继续。

### 8.3 低空间状态恢复（R16）

- 默认阈值 256 MiB（Q-P11）；可通过 CLI 参数配置。
- 启动时查询；低于阈值进入低空间状态。
- 低空间状态：读正常；写请求在追加前拒绝；Broker 进程存活。
- Storage Worker 每批追加前复查，并至少每秒复查一次；空间恢复后退出低空间状态。
- 预检通过但 `write` 失败：该条不 ack；进入/保持低空间状态；恢复时截断残缺尾部。

### 8.4 边界用例表

| 用例 | 预期行为 | 依据 | 对应验收 |
| --- | --- | --- | --- |
| 空分段文件 | 视为空 active；`next_offset = base_offset`；文件保留；索引可为空 | R7/R27 | V1、V2 |
| 半条记录 | 截断 active 到最后有效记录结束位置；不占 offset、不 ack | R7/R27 | V1 |
| 最后一条 CRC 损坏 | 从该记录起点截断 active；之前记录保留；`next_offset` 前移 | R7 | V1 |
| 跨分段基址不连续 | 不改任何文件；该分区标记不可用并告警；同 Topic 其他分区与其他 Topic 正常服务；不做 Topic 级降级 | R2/R27/D-04-2/D-04-6 | V1 |
| 封存分段损坏 | 不修改封存段；该分区标记不可用并告警；其他分区正常；全量校验仅测试/编译期选项 | R7/S-11/D-04-1/D-04-3 | V1（可选全量校验） |
| Topic 元数据损坏 | 跳过该 Topic + 告警（含 Topic 名与文件路径）；其他 Topic 正常 | R30/S-14 | V1 |
| 元数据存在但日志缺失 | 跳过该 Topic + 告警（含 Topic 名与缺失日志路径）；不伪造空日志 | R30/S-14 | V1 |
| 位点单槽损坏 | 使用另一有效槽；告警；重复窗口回退到该快照 | R28 | V2 |
| 位点双槽损坏 | 视为无已提交位点；告警；Broker 启动；消费者按 `--from` 开始 | R28/R11 | V2（损坏场景） |
| 残留 `.tmp` | 启动忽略；不删除；不作为有效数据 | R30/R28 | V1、V2 |
| 磁盘写满中途崩溃 | 该条不 ack；恢复截断 active 尾部；已有 acked 数据可读；释放空间后恢复写入 | R16/R1/R7 | V6 |
| 索引缺失/损坏 | 从日志重建；消息数据不受影响；索引不单独保证 | S-04 | V1、V11 |
| 单条记录超过 1 MiB | 协议校验/追加前校验拒绝；不写入、不截断 | R17/S-09 | V7 |

> 注：D-04-1、D-04-2、D-04-6 已裁决为**分区级降级、不修改封存段/不改文件、不做 Topic 级降级**；D-04-3 已裁决 `--verify-storage` **不进入 Broker CLI**。详见第 12 节。

## 9. 与 03 架构的落点核对

### 9.1 Storage Worker 内调用顺序

1. M5 校验 Topic/分区/`record_size`（协议请求校验）。
2. M5 路由到该分区所属 Storage Worker。
3. 磁盘空间预检（默认 256 MiB）。
4. 分配 `next_offset`。
5. 构造记录并计算 CRC32。
6. 追加到 active segment（页缓存）。
7. 追加成功 → 该条结果 `ok + offset`。
8. IO 线程编码响应 → 客户端收到 ack。
- 无 fsync；无热路径同步日志；同分区单 writer。

### 9.2 R23 批量逐条结果

- Storage Worker 对批次内同分区条目按输入顺序逐条追加。
- 每条独立结果：成功含 offset；失败含原因（如 `disk_full`、`message_too_large`），不分配 offset、不写。
- **AD-14**：同分区首个失败后，后续同分区条目不追加；列入失败/未尝试；其他分区继续。
- 批量结果的协议编码属 05；存储层只产出逐条结果。

### 9.3 分区亲和与 offset

- 每分区只属于一个 Storage Worker；该 worker 独占日志句柄、`next_offset`、索引与写入顺序。
- 无分区锁；单线程串行保证 R2。
- Group-shard Storage Worker 处理位点快照；与消息日志写入不共享可变状态。
