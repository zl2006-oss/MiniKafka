## 1. 术语与不变量

| 术语 | 含义 |
| --- | --- |
| Record | 一条消息的完整存储记录，自描述、可独立校验 |
| Segment | 分区 commit log 的一段连续文件；记录不跨段 |
| Base Offset | 分段内第一条记录的 offset；同时作为分段文件名 |
| Next Offset | 该分区下一条待写入记录的逻辑 offset（R27） |
| Committed Offset | 消费组已提交的“下一条待消费 offset”；所有 `< committed_offset` 的 offset 视为已处理 |
| Active Segment | 当前可追加的最后一段 |
| Sealed Segment | 已滚动、不再追加的历史分段 |
| Snapshot Slot | 位点文件的 A/B 两个完整快照之一 |

**必须始终满足的不变量**

1. 分区内 offset 从 0 开始单调递增、无空洞、不复用（R2/R27）。
2. 记录不跨分段；分段文件内只包含完整记录，尾部残缺在恢复时截断（R7）。
3. 已 ack 的记录必然完整写入页缓存；ack 路径不做 fsync（R1）。
4. 同一条记录的长度、CRC、key/value 长度必须自洽；任一不自洽即视为损坏。
5. 同一分区同一时刻只有一个 Storage Worker 写入；写入顺序 = offset 分配顺序 = 消费顺序（R2）。
6. 位点文件损坏时回退到上一份完整快照；不得阻止 Broker 启动（R28）。
7. Topic 元数据损坏只影响该 Topic；不得阻止 Broker 启动（R30）。
8. 封存分段只读不可变；恢复只截断 active segment，绝不修改历史分段（S-11）。
9. 索引是派生数据，崩溃后从日志重建，不单独做可靠性保证（S-04）。
10. 历史消息分段不可删除、不可修改；位点双槽与元数据原子写临时文件允许 rename 覆盖（S-10）。

## 2. 数据目录总览

与 03 第 7.2 节一致；目录层级只在本文固定，具体实现细节在 04 展开。

```text
<data-dir>/                              # 默认 ./data
├── meta/
│   ├── <topic>.meta                     # R30：每个 Topic 一个元数据文件
│   └── <topic>.meta.tmp                 # 原子写临时文件；启动时忽略
├── topics/
│   └── <topic>/                         # Topic 名已通过字符集校验
│       └── <partition>/                 # 十进制分区号，如 0、1、…、15
│           ├── 00000000000000000000.log  # 分段：base offset 为 20 位十进制
│           ├── 00000000000000000000.index
│           ├── 00000000000000012345.log
│           └── 00000000000000012345.index
└── groups/
    └── <group>/
        └── <topic>/
            ├── offsets.a                # 完整位点快照槽 A
            └── offsets.b                # 完整位点快照槽 B
```

**规则**

- Topic 名必须已通过 Q-P8 的 `[a-z0-9_-]{1,64}` 校验；不得直接使用未校验的用户输入拼路径。
- Group 名按 R31 与 Q-P8 完全一致：仅允许 `[a-z0-9_-]{1,64}`；禁止 `/`、`..` 与空名。目录映射直接使用合法 Group 名，不做 percent-encode。
- 分区号只允许十进制 `0..partitions-1`；分区数上限 16（R14）。
- `*.tmp` 文件是原子写的中间产物；启动扫描时**忽略**，不得当作有效数据。
- 不在目录树内放索引以外的派生数据（如全局 offset 索引）；如未来需要，必须作为独立规则补充。

## 3. 消息记录格式

### 3.1 字节序与总体布局

- **所有整数一律大端（network byte order）**（CLAUDE.md「# 4 协议设计规则」对二进制格式的统一要求；存储记录沿用）。
- 每条记录自描述；分段文件没有单独的文件头，文件由若干完整记录顺序拼接而成。
- 记录布局如下：

| 偏移 | 字节数 | 字段 | 类型 | 含义 |
| --- | --- | --- | --- | --- |
| 0 | 4 | `total_len` | uint32 BE | 本字段之后的字节数（含 CRC、头、key、value） |
| 4 | 4 | `crc32` | uint32 BE | 校验值；覆盖范围见 3.2 |
| 8 | 4 | `magic` | uint32 BE | 固定 `0x4D4B4146`（ASCII “MKAF”） |
| 12 | 2 | `version` | uint16 BE | 记录格式版本；MVP = 1 |
| 14 | 2 | `flags` | uint16 BE | bit0 = `KEY_PRESENT`；其余位 MVP 必须为 0 |
| 16 | 4 | `key_len` | uint32 BE | key 的 UTF-8 字节数；可为 0 |
| 20 | 4 | `value_len` | uint32 BE | value 的 UTF-8 字节数；可为 0 |
| 24 | `key_len` | `key` | UTF-8 bytes | 原始 UTF-8，无 NUL 终止符 |
| 24 + `key_len` | `value_len` | `value` | UTF-8 bytes | 原始 UTF-8，无 NUL 终止符 |

由此：

```text
record_size = 4 + total_len
total_len   = 20 + key_len + value_len
record_size = 24 + key_len + value_len
```

最小记录为 24 字节（`key_len = value_len = 0`）。

> **S-08 已确认**：MVP 不增加 `timestamp_ms`。R19 只要求输出 `partition/offset/key/value`；后续若需要时间戳，应提升 `version` 或在 flags 中预留扩展位。

### 3.2 CRC 算法与覆盖范围

**最终裁决：CRC32 IEEE**

| 候选 | 说明 | 结论 |
| --- | --- | --- |
| **CRC32 IEEE（反射多项式 `0xEDB88320`）** | 测试向量成熟、可自证实现正确；100B 记录下硬件加速无实际收益 | **采用** |

- 标准测试向量：ASCII `"123456789"` → **`0xCBF43926`**（CRC32 IEEE，反射多项式 `0xEDB88320`，初值 `0xFFFFFFFF`，最终异或 `0xFFFFFFFF`）。
- 实现必须固定初值、反射规则与最终异或，跨版本不得改变；至少包含空串、单字节、`"123456789"` 测试向量。

**覆盖范围（S-02 已确认：覆盖长度字段）**

```text
crc_input = bytes[0, 4)          # total_len（4 字节）
          + bytes[8, record_size)  # magic/version/flags/key_len/value_len/key/value
crc 字段自身 bytes[4, 8) 不参与
```

- 覆盖 `total_len` 的目的：长度字段被破坏时，CRC 校验也会失败；配合“长度越界/不自洽”检查，避免把错误长度当成合法边界。
- **不覆盖 CRC 字段本身**是 CRC 的标准做法。
- **不采用**“不覆盖长度字段”的方案；该方案只能依赖长度范围检查与后续记录校验，鲁棒性不足。
- CRC 实现必须提供固定测试向量（至少空串、单字节、`"123456789"` → `0xCBF43926`），跨版本不得改变。

### 3.3 长度字段与半条记录识别

恢复时按以下顺序判断：

1. 从当前位置读取 4 字节 `total_len`；剩余不足 4 字节 → **半条头部**，尾部截断。
2. 检查 `total_len >= 20`；否则长度非法。
3. 计算 `record_size = 4 + total_len`；若 `record_size > 1 MiB` → 非法（超过 R17 上限）。
4. 若“当前位置 + record_size”超过文件末尾 → **半条记录**，尾部截断。
5. 读取完整记录，检查 `magic`、`version`、`flags`、`key_len`、`value_len` 自洽性：
   `total_len == 20 + key_len + value_len`。
6. 计算 CRC 并比对；失败 → 从该记录起点截断。
7. 全部通过 → 该记录有效，继续下一条。

> 注意：`total_len` 是“本字段之后”的长度，包含 CRC 字段；因此 `record_size = 4 + total_len`。

### 3.4 单条 1MB 上限（R17）

- **判定口径（S-09 已确认）**：`record_size <= 1,048,576` 字节，即“存储头 + key + value”总量不超过 1 MiB。
- 写入前判定：Broker Core 在协议请求校验阶段先做一次；Storage Worker 在追加前再做一次。两次都必须拒绝，不得截断。
- 超限错误由协议层返回明确错误（具体错误码属 05）；存储层不得写入部分记录。
- 协议帧头与批量请求头不计入单条 1MB；R17 已回写口径澄清：1MB 指存储记录（存储头 + key + value）≤ 1 MiB。

### 3.5 key/value 编码与 flags

- `key`、`value` 都是**原始 UTF-8 字节**，无 NUL 终止符，长度由 `key_len`/`value_len` 指定（R19/Q-P14）。
- `flags.bit0 = KEY_PRESENT`：
  - `1`：客户端提供了 key，即使 `key_len = 0`（空字符串）也算“有 key”，参与哈希分区（R14/R22）。
  - `0`：key 缺失/null（无 key），走轮询分区；此时 `key_len` 必须为 0。
- `value` 必须存在；空字符串时 `value_len = 0` 合法。
- 写入前必须校验 UTF-8 合法；非法 UTF-8 拒绝，不写入、不截断。
- 不支持二进制/base64（Q-P14 将二进制列为 P1）；若未来支持，必须提升 `version` 或引入明确的编码标志。

## 4. 分段文件与索引

### 4.1 命名规则

```text
<data-dir>/topics/<topic>/<partition>/<base_offset:020d>.log
<data-dir>/topics/<topic>/<partition>/<base_offset:020d>.index
```

- `<base_offset>` 是该分段第一条记录的 offset，20 位十进制（64 位 offset 的最大十进制宽度），保证字典序 = 数值序。
- 不可使用自增序号或时间戳命名；base offset 是分段身份的一部分。
- 分段文件只包含完整记录；文件名不包含 key、Topic 名以外的可变信息。
- 索引文件与分段文件一一对应；索引缺失/损坏可重建，不影响正确性。

### 4.2 滚动触发条件

1. 追加前计算 `new_size = active_size + record_size`。
2. 若 active segment 非空且 `new_size > segment_bytes` → 先封存 active，创建新分段，`base_offset = next_offset`。
3. `--segment-bytes` 下限为 2 MiB；单条记录上限 1 MiB，因此正常配置下 `record_size < segment_bytes`。若配置/校验异常导致 `record_size > segment_bytes`，拒绝该条；不创建超大分段。
4. 新分段创建后，在索引中加入 `(base_offset, 0)` 检查点。
5. 同一分区的滚动、关闭、创建新分段均由该分区的 Storage Worker 串行执行。

### 4.3 分段大小默认值（B5）

| 候选 | 100B 记录约容纳条数 | 100k 条/秒下约多久滚动 | 评价 |
| --- | --- | --- | --- |
| 64 MiB | ~640k | ~6.4s | 滚动过频，测试期间产生大量文件 |
| 128 MiB | ~1.28M | ~12.8s | 可接受，但仍有频繁滚动 |
| **256 MiB（定稿）** | ~2.56M | ~25.6s | 滚动开销与文件数量平衡；恢复扫描可控 |
| 512 MiB | ~5.12M | ~51.2s | 文件更大，单次恢复扫描更慢 |
| 1 GiB（Kafka 常见） | ~10.2M | ~102s | 更少滚动，但演示 VM 上文件偏大、恢复扫描偏慢 |

- **定稿默认 256 MiB**，通过 `--segment-bytes` 可配置，**下限 2 MiB**；默认值固定写入文档（R20）。
- 依据：在 100B payload、10 万条/秒目标下避免数秒一次滚动；同时让恢复扫描和文件管理保持在演示可控范围。
- 分段大小不改变正确性，只影响滚动频率、恢复扫描时间与文件数量。

### 4.4 索引结构与粒度

**候选**

| 候选 | 查找复杂度 | 写入/空间代价 | 评价 |
| --- | --- | --- | --- |
| **稀疏索引（定稿）** | O(log S + log I + G)，G 为检查点间隔内记录数 | 每 4 KiB 一个 12 字节条目，开销约 0.3% | 查找快，写入开销低，可重建 |
| 无索引 | O(该分段记录数) | 0 | 实现最简，但大分段按 offset 定位慢 |
| 稠密索引 | O(log S + 1) | 每条记录一个条目，索引约为日志的 5%–10% | 查找最快，但写入与空间开销大 |

- **定稿：稀疏索引**：日志数据每增长 4 KiB 追加一个检查点（首条记录的位置 0 必须有检查点）。
- 索引条目固定 12 字节：

```text
offset   : uint64 BE   # 记录的逻辑 offset
position : uint32 BE   # 记录在分段文件内的字节偏移
```

- 分段默认 256 MiB < 4 GiB，`position` 用 uint32 足够；若未来允许分段 >4 GiB，必须升级索引格式并提升版本。
- 索引文件无文件头；若文件长度不是 12 的整数倍或条目 offset 非递增，视为损坏并重建。
- **索引是派生数据，不是正确性来源**：崩溃后从日志重建，不单独做可靠性保证；缺失/损坏时 Storage Worker 扫描分段重建，不影响 offset 与消息数据（S-04）。

### 4.5 按 offset 定位算法

1. 在分区的分段列表中二分查找 `base_offset <= target` 的最大分段（列表可按需从目录扫描构建并缓存）。
2. 读取该分段索引；二分查找最后一个 `offset <= target` 的检查点。
3. 从该检查点的 `position` 开始顺序扫描记录，直到 `record.offset == target` 或越过 target。
4. 找不到 target → 返回 `offset_out_of_range`（05 定义错误码）；回放/消费按 03 的边界规则处理。
5. 索引缺失：从分段起点顺序扫描（O(分段记录数)），并重建索引。

**复杂度**：有索引时 O(log 段数 + log 索引条目 + 检查点间隔内记录数)；无索引时 O(段内记录数)。检查点间隔 4 KiB 意味着平均扫描约 40 条 100B 记录，满足演示与吞吐场景。

## 5. offset 与保序

### 5.1 分配规则（R2/R27）

- offset 是**分区内单调递增的逻辑序号**，与物理字节位置、分段文件名解耦。
- 由该分区唯一所属的 Storage Worker 在追加前分配：`next_offset` 从 0 开始，每成功追加一条 +1。
- 失败条目不分配 offset；不写记录；不占用 offset。
- 分区内严格串行：同一分区同一时刻只有一个追加任务在执行；跨分区可并行。
- 批量逐条结果：同一批内同分区条目按输入顺序处理；某条失败后，该分区后续条目不再追加（AD-14），其他分区继续。

### 5.2 崩溃后重建 `next_offset` 的完整步骤

> S-11 已确认：从最后一个分段向前回退扫描；全量校验仅作为可选模式（`--verify-storage`/测试）。此处给出完整算法。

1. 枚举 `<partition>/` 下所有 `*.log`，按 `base_offset` 升序排序；忽略 `*.tmp`。
2. 若没有任何分段：`next_offset = 0`，创建 base=0 的空分段。
3. 从**最后一个分段**开始：
   1. 校验文件名 base 与第一条有效记录的 offset 是否一致；不一致 → 该分段不可信，回退到前一分段。
   2. 从分段起点（或最后一个可信索引检查点）顺序读取记录，按第 3.3 节规则校验。
   3. 记录最后一条有效记录的 `offset` 与其结束位置；遇到第一条无效/不完整记录即停止。
   4. 若 **active segment** 存在无效/不完整尾部：`ftruncate` 到最后有效记录结束位置；**封存分段只读，不得截断/修改**。
   5. `next_offset = 最后有效 offset + 1`；若该分段没有任何有效记录，`next_offset = base_offset`。
4. 若最后一个分段不可用（空文件且 base 与前一分的 next 不连续、首条记录非法、基址不一致等），按同样方式检查前一分段；封存分段只读，若封存段损坏则停止在该段并告警，不修改历史分段；直到找到可信边界。
5. 若所有分段都不可用：`next_offset = 0`，保留文件并在 stderr 告警；是否重建空分段由 04 明确。
6. 重建被扫描分段的稀疏索引；未扫描的封存分段索引若缺失，可在首次读取时按需重建。
7. 校验并更新分区元数据（若有缓存）；恢复完成后才允许 acceptor 启动（AD-16）。

**说明（S-11 已确认）**

- R27 要求“扫描分段尾部重建”；定稿为“最后分段 + 必要时向前回退”，而不是每次启动全量扫描所有历史记录。全量校验仅作为可选模式（`--verify-storage` 或测试模式）。
- 封存分段只读不可变；恢复只截断 active segment，绝不修改历史分段。运行期封存段损坏在可选全量校验或读取时暴露；全量校验的性能代价在 04 说明。
- 空分段文件（0 字节）视为合法的空 active 分段；`next_offset = base_offset`，文件保留（不做物理删除）。
- 分段基址不连续（例如缺少中间分段）→ 停止在该边界，告警；不得让 offset 出现空洞后继续服务。

## 6. 位点文件（R28）

### 6.1 位置与文件

```text
<data-dir>/groups/<group>/<topic>/offsets.a
<data-dir>/groups/<group>/<topic>/offsets.b
<data-dir>/groups/<group>/<topic>/offsets.tmp   # 写入中间文件，启动时忽略
```

- 每个 `(group, topic)` 目录下有两个完整快照槽；快照包含该组在该 Topic 下**所有分区**的已提交位点。
- `committed_offset` 语义：下一条待消费的 offset；`offset < committed_offset` 视为已处理。

### 6.2 格式（已确认）

```text
Header:
  magic              uint32 BE   # "MKOF" = 0x4D4B4F46
  version            uint16 BE   # 1
  header_size        uint16 BE   # 24
  generation         uint64 BE   # 单调递增
  entry_count        uint32 BE
  reserved           uint32 BE   # 0

Entries (entry_count 个，每个 12 字节):
  partition          uint32 BE
  committed_offset   uint64 BE

Footer:
  crc32              uint32 BE   # 覆盖 Header + Entries（不含 Footer 自身）
```

- 文件大小 = 24 + 12 × `entry_count` + 4。
- `entry_count = 0` 合法（该组尚无位点）。
- 所有整数大端；CRC 算法与记录格式保持一致（S-01）。
- 写入内容必须自洽：`header_size == 24`，`entry_count` 与文件长度匹配，分区号在合法范围。

### 6.3 写入时机（R6、Q-P4、Q-P6）

1. **自动提交**：客户端每 `--auto-commit-interval`（默认 5s，Q-P4）提交“已处理位点”；Broker 的 Group-shard Storage Worker 更新内存位点后写入快照。
2. **正常退出补提交**：Consumer 在 Ctrl+C / `--exit-at-end` 正常退出前补一次提交（Q-P6）；仍走同一写入路径。
3. **提交成功时点**：位点快照写入页缓存并完成 rename 后返回成功；**不 fsync**（R28 与 R1 同一可靠性口径）。
4. **提交失败**：返回错误；客户端按 R8 退避重试并告警，进程不退出。
5. **写入粒度**：每次提交写一份完整快照（该 group/topic 所有分区）。提交频率低（默认 5s），实现简单、恢复快。

### 6.4 轮转与“上一份完整位点”（已确认）

- 两个槽 `offsets.a` / `offsets.b` 各保存一份完整快照，`generation` 递增。
- 写入流程：
  1. 序列化新快照到 `offsets.tmp`（同目录，保证 rename 不跨文件系统）。
  2. 将 `offsets.tmp` **rename 覆盖 generation 较旧的槽**。
  3. 另一个槽保持为上一份完整快照；最新槽为当前快照。
- 进程崩溃：
  - 若崩溃在 `offsets.tmp` 写入期间：两个正式槽均未被修改；恢复使用旧最新槽。
  - 若崩溃在 rename 之后：新槽完整（rename 原子）；恢复使用新槽。
- 历史消息分段不可删除、不可修改；位点双槽与元数据原子写临时文件允许 rename 覆盖（S-10 已确认）。

### 6.5 损坏回退流程

1. 启动时读取 `offsets.a` 与 `offsets.b`，忽略 `offsets.tmp`。
2. 对每个槽校验：magic、version、header_size、entry_count、文件长度、CRC、分区号范围。
3. 取**通过校验且 generation 最大**的槽作为当前位点。
4. 若一个槽损坏、另一个有效：使用有效槽，stderr 告警；损坏槽保留原位，不删除。
5. 若两个槽都损坏：视为“无已提交位点”；stderr 告警；Broker 仍启动（R28 不要求位点损坏阻止启动）。该 group 下次消费按 R11 的 `--from` 从零/末尾/指定位点开始。
6. 回退造成的重复窗口：
   - 正常自动提交间隔内崩溃：最多重复约 5s 的已处理消息（R6）。
   - 回退到上一快照：重复窗口扩大到上一快照之后的所有已处理消息；仍满足至少一次，不丢消息（R28）。
   - 与 V2 的关系：V2 验收“重启从最后已提交位点继续；重复不超过一个自动提交间隔”；正常路径应满足；人为损坏位点文件时允许回退到上一快照，重复窗口可能更大，验收脚本应区分“正常崩溃”与“位点损坏”两种场景。

### 6.6 备选方案（未采用）

| 方案 | 优点 | 缺点 | 评价 |
| --- | --- | --- | --- |
| **双文件快照轮转（采用）** | 有界、恢复快、直接提供上一完整快照 | 每次写全量快照；rename 覆盖旧槽 | 已采用 |
| 追加式日志 | 天然保留历史，无需覆盖 | 文件增长；恢复需从尾部找最后有效记录 | 未采用 |
| 单文件双槽（固定/变长） | 文件少、原子切换 | 变长记录与槽切换复杂 | 未采用 |

## 7. Topic 元数据（R30）

### 7.1 位置与文件

```text
<data-dir>/meta/<topic>.meta
<data-dir>/meta/<topic>.meta.tmp   # 原子写中间文件；启动时忽略
```

- 每个 Topic 一个文件；单文件损坏只影响该 Topic，满足 R30“单个元数据损坏跳过”。
- 文件名中的 Topic 名必须已通过 Q-P8 字符集校验。

### 7.2 格式（已确认）

```text
magic            uint32 BE   # "MKTM" = 0x4D4B544D
version          uint16 BE   # 1
flags            uint16 BE   # 0
partition_count  uint32 BE   # 1..16
name_len         uint32 BE
name             UTF-8 bytes # Topic 名
crc32            uint32 BE   # 覆盖以上所有字节（不含 crc 自身）
```

- 所有整数大端。
- 校验：magic、version、flags=0、`1 <= partition_count <= 16`、`name_len` 与文件长度匹配、name 合法、CRC 正确。
- 元数据只记录“Topic 名称 + 分区数”；不记录消息数据或已提交位点。

### 7.3 原子写

1. 在 `<data-dir>/meta/` 下创建 `<topic>.meta.tmp`。
2. 写入完整内容并关闭文件（页缓存；不要求 fsync）。
3. `rename(<topic>.meta.tmp, <topic>.meta)`；同目录 rename 原子替换。
4. 启动时忽略残留 `*.tmp`；不删除。

### 7.4 启动扫描与损坏处理

1. 枚举 `<data-dir>/meta/*.meta`，忽略 `*.tmp`。
2. 逐个校验格式与 CRC。
3. 有效：加入 M5 的 Topic 候选列表。
4. 损坏/非法：**跳过该 Topic + stderr 告警**；告警必须包含 Topic 名与（若涉及）缺失的日志路径；其他 Topic 继续加载；不得阻止 Broker 启动（R30/S-14）。
5. 文件名与内部 name 不一致：视为损坏，跳过并告警。
6. 分区数非法：跳过并告警。
7. 不自动删除、不自动修复损坏文件；修复方式由用户/后续工具决定。

### 7.5 创建与生产并发时的可见性（AD-15）

1. Topic 创建由 M5 控制面串行处理：
   1. 创建 `<topic>/` 与各分区目录、初始空分段（base=0）。
   2. 原子写 `<topic>.meta`。
   3. 构造新的不可变 Topic 快照（copy-on-write），原子替换当前快照。
2. 在快照替换前，新 Topic 对 Producer/Consumer 不可见；已有请求继续使用旧快照，不会看到半成品。
3. 若崩溃发生在步骤 1 与 2 之间：留下无元数据的日志目录；启动扫描时忽略并告警，不对外提供 Topic。
4. 若元数据存在但某个分区目录/分段缺失：该 Topic 视为不完整；启动时跳过并告警，**告警必须包含 Topic 名与缺失的日志路径**；**不自动伪造空日志**（避免掩盖数据丢失，S-14）。
5. 创建完成后，新 Topic 立即可被后续请求看到；分区数不可变（R14）。

## 8. 恢复流程与边界用例

### 8.1 Broker 启动到 acceptor 就绪的顺序（AD-16）

1. 解析命令行参数，确认 `<data-dir>` 可读写；不存在则创建。
2. 扫描 `meta/*.meta`，校验并加载有效 Topic；损坏 Topic 跳过 + 告警（R30）。
3. 对每个 Topic/Partition：
   1. 枚举分段，按 base offset 排序。
   2. 从最后分段向前回退，按第 5.2 节重建 `next_offset`；截断无效尾部（R7/R27）。
   3. 重建/校验稀疏索引；缺失则重建。
4. 扫描 `groups/*/*/offsets.a|b`，校验位点快照；选择最新有效 generation；损坏回退（R28）。
5. 初始化磁盘空间状态：读取可用空间；低于 256 MiB 阈值则进入低空间状态（只读可服务，写请求拒绝）——具体阈值见 03/Q-P11。
6. 启动 Storage Worker、IO Reactor、Logger 线程。
7. 启动 acceptor，输出 ready；**在此之前不接收客户端请求**。

### 8.2 边界用例表

| 用例 | 输入/状态 | 预期行为 | 依据 |
| --- | --- | --- | --- |
| 空分段文件 | 0 字节 `.log`，base offset 已知 | 视为空 active 分段；`next_offset = base_offset`；文件保留；索引可为空 | R7/R27 |
| 半条记录 | 文件尾只有不完整头部或不足 `record_size` | 截断到最后一条有效记录结束位置；半条不占用 offset；不 ack | R7/R27 |
| 最后一条 CRC 损坏 | 最后一条记录长度完整但 CRC 不符 | 从该记录起点截断；之前记录保留；`next_offset` 前移 | R7 |
| 跨分段边界 | 记录不跨段；active 段尾出现部分记录，或封存段损坏 | active 段尾部分记录截断；封存段只读，不得截断/修改；封存段损坏则停止在该段并告警，不从后续段继续 | R7/R2/S-11 |
| Topic 元数据损坏 | `<topic>.meta` CRC/格式非法 | 跳过该 Topic + stderr 告警（含 Topic 名与文件路径）；其他 Topic 正常；Broker 启动 | R30/S-14 |
| 位点文件损坏 | 一个槽 CRC 非法，另一个有效 | 使用另一个槽；告警；重复窗口回退到该快照；Broker 启动 | R28 |
| 位点文件两槽均损坏 | 两个槽都非法 | 视为无已提交位点；告警；Broker 启动；消费者按 `--from` 重新开始 | R28/R11 |
| 磁盘写满中途崩溃 | 预检通过后写入失败，或写一半崩溃 | 该条不 ack；恢复时截断残缺尾部；已有 acked 数据可读；释放空间后恢复写入；Broker 不崩溃 | R16/R1/R7 |
| 索引缺失/损坏 | `.index` 不存在、长度非 12 倍数、offset 非递增 | 从日志重建索引；消息数据不受影响；索引不单独做可靠性保证 | R7/S-04 |
| 分段基址不连续 | 分段列表缺少中间 base，或首条记录 offset != base | 停止在可信边界；告警；不得产生 offset 空洞后继续服务 | R2/R27 |
| 元数据存在但分区日志缺失 | `.meta` 有效，但 `<topic>/<partition>/` 不存在 | 跳过该 Topic + 告警（必须含 Topic 名与缺失日志路径）；不伪造空日志；不阻止其他 Topic | R30/S-14 |
| 残留 `.tmp` 文件 | `meta/*.tmp` 或 `groups/**/offsets.tmp` | 启动时忽略；不删除；不作为有效数据 | R30/R28 |
| 单个记录超过 1MB | 写入前校验 `record_size > 1MiB` | 拒绝；不写入；不截断；返回明确错误 | R17 |

### 8.3 低空间状态恢复（R16）

- 启动时读取可用空间；低于阈值（默认 256 MiB，Q-P11）→ 低空间状态。
- 低空间状态：读路径正常；写请求在追加前被拒绝，返回明确错误；Broker 进程存活。
- Storage Worker 周期性复查（例如每秒或每批）可用空间；恢复后退出低空间状态。
- 预检通过但 `write` 失败：该条不 ack；恢复时按 R7 截断残缺尾部；不得仅依赖 `write` 返回值。

## 9. 与 03 架构的落点核对

### 9.1 Storage Worker 追加调用顺序

```text
Broker Core 校验（Topic/分区/record_size）
  → 路由到该分区的 Storage Worker
  → 磁盘空间预检（R16，默认阈值 256 MiB）
  → 分配 next_offset（R27）
  → 构造记录（长度/CRC/magic/version/flags/key/value）
  → 追加写入当前 active segment（页缓存）
  → 追加成功返回（记录完整进入页缓存）
  → 生成该条成功结果 + offset
  → IO 线程编码响应（客户端此时才收到 ack）
```

- **fsync 不在该链路**（R1）；ack 语义在“追加成功返回”时成立。
- 若预检失败：不分配 offset、不写记录、不 ack。
- 若写入失败/部分写入：该条不 ack；恢复时截断残缺尾部。
- 同分区批内首个失败后，后续同分区条目不追加；其他分区继续（AD-14）。

### 9.2 R23 批量逐条结果在存储层如何产生

- Storage Worker 对批次内条目按顺序逐条调用追加逻辑。
- 每条独立产生结果：`{index, partition, offset, status, error}`。
- 成功条目包含分配的 offset；失败条目不分配 offset，包含原因（如 `disk_full`、`message_too_large`）。
- 同分区首个失败后，该分区后续条目标记为未尝试/阻塞；其他分区继续。
- 批量结果由 IO 线程编码为协议响应；具体编码属 05。

### 9.3 分区亲和与 offset

- 每个分区只属于一个 Storage Worker；该 worker 独占分区日志句柄、`next_offset`、索引与写入顺序。
- 无分区锁；单线程串行保证 R2。
- Group-shard Storage Worker 负责位点快照，与消息日志写入互不共享可变状态。

## 12. 禁止项

1. **不引入第三方库**；CRC、索引、文件操作均使用标准库 + POSIX。
2. **ack 路径不做 fsync**（R1）；位点提交同样不额外 fsync（R28）。
3. **历史消息分段不可删除、不可修改**；不做保留期清理（R25）。位点双槽与元数据原子写临时文件允许 rename 覆盖（S-10 已确认）。
4. **热路径不做同步日志**：每条消息的 produce/fetch 不写日志；只记录错误/恢复/状态变化。
5. **不定义网络帧格式、报文字段、错误码表**（属 05）。
6. **不写业务代码**；本文只定义规则与格式约束。
7. 不引入 protobuf、boost、gRPC 或现成网络/MQ 库。

## 13. 裁决汇总（已确认）

| 编号 | 问题 | 候选 | 裁决 | 状态 |
| --- | --- | --- | --- | --- |
| Q-S1 | CRC 算法 | CRC32 IEEE / 其他 | **CRC32 IEEE（`0xEDB88320`；`"123456789"` → `0xCBF43926`）** | 已确认 |
| Q-S2 | CRC 是否覆盖 `total_len` | 覆盖 / 不覆盖 | **覆盖；排除 CRC 字段自身** | 已确认 |
| Q-S3 | 分段大小默认值 | 64 / 128 / 256 / 512 MiB | **256 MiB；`--segment-bytes` 下限 2 MiB** | 已确认 |
| Q-S4 | 索引结构 | 稀疏 / 无 / 稠密 | **稀疏，4 KiB 粒度；派生数据，从日志重建** | 已确认 |
| Q-S5 | 位点文件策略 | 双文件轮转 / 追加式 / 单文件双槽 | **双文件轮转** | 已确认 |
| Q-S6 | Topic 元数据组织 | 每 Topic 文件 / 单文件 | **每 Topic 文件** | 已确认 |
| Q-S7 | Group 名目录安全规则 | 同 Topic 字符集 / percent-encoding | **`[a-z0-9_-]{1,64}`（R31）** | 已确认 |
| Q-S8 | 是否存时间戳 | 不存 / 存 `timestamp_ms` | **MVP 不存** | 已确认 |
| Q-S9 | 1MB 上限口径 | 仅 value / 含 key+存储头 / 含协议头 | **`record_size`（存储头+key+value）≤ 1 MiB；协议帧头与批量请求头不计入** | 已确认 |
