# miniKafka 需求文档

> 状态：需求澄清完成（评审意见已合入，含 R30/R31 补充）｜最后更新：2026-11-13
> 定位：**演示验证型学习项目**（固定，不按长期生产系统对待）
> 说明：第 3 节是需求澄清的初始输入，**最终口径以第 4 节为准**；两者冲突时以第 4 节为准。未在第 4 节确认的内容不得当作既定需求。

---

## 1. 项目概述

用 C++ 从零实现的类 Kafka 消息队列（miniKafka），运行于 Linux，包含三个角色：

- **Broker**：服务端，topic/分区/消息存储与位点管理的宿主；
- **Producer**：生产者客户端，命令行工具；
- **Consumer**：消费者客户端，命令行工具。

**项目定位**：演示验证型学习项目。目标是可在单机演示、可复现、可验收地展示消息队列的核心机制（持久化、顺序、位点、消费组、崩溃恢复），不承担长期生产业务。

## 2. 用户与使用者

| 使用者 | 说明 |
| --- | --- |
| Producer CLI | 生产者客户端程序，通过 TCP 向 Broker 发消息 |
| Consumer CLI | 消费者客户端程序，以 Consumer Group 身份拉取消息 |
| 命令行操作者（开发者 / 学习者 / 演示者） | 通过 CLI 创建 topic、发消息、起消费者、做演示与验收 |
| Broker 运维者 | 启停、观察 Broker 的人（MVP 无 Web 界面） |

说明：定位为演示验证型学习项目，使用者以开发者/学习者为主；本项目不承诺生产级运维能力。

## 3. 初始功能清单（输入）

> 本节保留用户最初的设想，仅作为需求澄清的输入记录；**最终口径以第 4 节为准**。

1. 创建 Topic：创建时指定分区数，上限 16；
2. 列出 Topic 及分区信息；
3. Producer 通过 TCP 长连接发送消息（单条/批量），可指定分区或按键哈希选分区；Broker 确认写入后返回成功；支持超时重试；
4. Consumer 以 Consumer Group 身份消费：同一 Group 内一个分区只分配给一个消费者；按 offset 拉取，可从 earliest / latest / 指定位点开始；
5. 消息持久化：commit log 顺序追加写磁盘，分段文件管理；
6. 消费位点由消费者提交，Broker 持久化保存；
7. Broker 被 kill -9 后重启：消息不丢、位点可恢复；消费者中断后重启，从中断位点继续消费；
8. 支持按 offset 重放消息；投递语义为至少一次（允许重复消费）。

## 4. 已确认结论（最终口径）

> 以下为经逐轮确认、并已合入评审修订的结论，可直接进入设计。

**R1｜Broker ack 的持久化边界 = 进程级持久化（第 1 轮确认）**
- Broker 将消息写入操作系统页缓存后即返回 ack，**不要求**在 ack 路径上做显式磁盘同步。
- 故障覆盖：进程崩溃 / `kill -9` 不丢；**机器宕机 / 掉电允许丢失最近若干条尚未刷盘的消息**。这是显式声明的能力边界，不对外表述为"永不丢"。
- 因此验收口径以"进程崩溃后恢复"为准，不以"断电恢复"为验收条件。
- 由此排除"逐条同步落盘后 ack"方案，性能目标（10 万条/秒、P99 < 10ms）与 ack 语义不冲突。

**R2｜同一分区内严格保序（第 2 轮确认）**
- 同一分区内消息按 Broker 接受顺序被消费，offset 严格递增。
- 生产端超时重试必须保序：重试未成功前，该分区后续消息不得越过它；同一分区同一时刻只允许一条消息"在途"（批量发送时按批次整体保序）。
- 分区之间可并行，总吞吐不受单分区串行约束影响。
- "按 offset 重放"的语义因此是确定的顺序重放。

**R3｜Producer 重试耗尽 = 明确失败（第 3 轮确认）**
- 重试次数与总超时均可配置；重试耗尽后打印明确错误（含分区、消息位置、失败原因），以非 0 退出码结束，**不静默丢弃消息**。
- "至少一次"的可承诺边界 = **已收到 Broker ack 的消息**；未收到 ack 的消息由调用方决定是否重发。
- 重试导致的重复消费被接受，不做去重（用户原始清单明确：允许重复消费）。

**R4｜"P99 < 10ms" = Producer ack 延迟（第 4 轮确认）**
- 计时区间：Producer 调用发送（单条或单批）→ 收到 Broker 的 ack。
- 目标：该延迟 P99 < 10ms（与 R1 的页缓存 ack 自洽）。
- 端到端投递延迟（Producer 发送 → Consumer 收到）仅作为观测指标，**不设硬性目标**，不纳入验收。

**R5｜"10 万条/秒" = Broker 总入口吞吐（第 5 轮确认）**
- 多个 Producer 并发写入、消息分布在多个分区，合计 ≥ 10 万条/秒（100B 消息）。
- 测试场景为**纯写**，不启动消费者；不要求单个 Producer 进程独立达到该值。
- 不要求读写混合场景下的吞吐指标。

**R6｜自动提交以"已处理"为准（第 6 轮确认）**
- 仅当消息成功交付给应用并处理完成（CLI 场景：已成功写入标准输出）后，内存中的已消费位点才推进。
- 自动提交定时器只是把"已处理位点"定期持久化；提交间隔只影响**崩溃后的重复窗口**，不影响正确性。
- 消费者崩溃后重启：最多重复消费"已处理但未提交"的区间，**不丢消息**；与 R3 的至少一次语义自洽。

**R7｜崩溃恢复 = 按长度 + CRC 校验并截断尾部（第 7 轮确认，评审补充判据）**
- Broker 启动时扫描分段文件，恢复判据为**记录长度字段 + CRC 校验**；以最后一条校验通过的记录为有效边界。
- **校验通过的记录一律保留，与是否已 ack 无关**；长度越界、CRC 失败或尾部不完整的记录被丢弃（截断）。
- 已 ack 消息必然完整写入页缓存，因此满足 R1；未 ack 但记录完整且校验通过的数据也可能保留，不构成对 R1 的违反。
- 恢复**不需要人工干预**，启动成功即对外提供服务（无需人工修复步骤）。

**R8｜位点提交失败 = 重试 + 告警，不退出（第 8 轮确认）**
- 提交失败后退避重试；若拉取仍可用则继续消费；与 Broker 连接断开则持续重连。
- 持续失败时周期性向 stderr 输出告警；进程不主动退出，由用户 Ctrl+C 结束。
- 结果仍满足至少一次：不丢消息，最多重复未提交区间。

**R9｜性能验收 = 固定基准机（第 9 轮确认，评审补充）**
- 指定一台固定的基准机器作为验收环境（Broker 单机部署），**基准机为 VMware Ubuntu 虚拟机**；配置固定为：**4 vCPU / 8 GiB 内存 / SSD 虚拟磁盘；宿主机 AMD Ryzen 7 7435HS（16 GB RAM）**。
- 所有性能验收在该环境上、用同一套脚本与固定参数执行。
- **压测工具必须用 C++ 实现**（见第 6 节）。
- **性能不达标时，以实测值如实记录并标注差距**，不得修改口径或选择性报告。

**R10｜动态 rebalance = P1（v1.1 可选）；MVP 采用启动时静态分配（第 10 轮原结论，评审修订）**
- **MVP**：组内消费者在启动时静态分配分区；成员加入/正常退出/崩溃均不触发重新分配；失效消费者负责的分区暂停消费，直到该消费者重新加入。
- **P1（v1.1 可选）**：成员加入、正常退出、心跳超时触发 rebalance，分区在存活成员之间重新分配，存活成员接管失效成员的分区；需配套成员心跳、会话超时、组协调机制。
- MVP 验收不包含动态接管；P1 验收包含"kill 掉一个消费者后其分区被存活成员接管"。
- 本节修订第 10 轮原结论（原为全自动 rebalance），以本节为准。

**R11｜已提交位点优先于起始位置策略（第 11 轮确认）**
- 若该 group 在该分区存在已提交位点，一律从已提交位点继续消费。
- earliest / latest / 指定位点仅在**无已提交位点**（首次消费、新 group、新分区）时生效。
- 因此"消费者中断后重启，从中断位点继续消费"得到保证；从中间重读必须通过重放能力或新 group 实现（重放语义见 R12）。

**R12｜"重放" = 只读回放（第 12 轮确认）**
- 按 topic / 分区 / offset（含区间或条数，具体参数在 CLI 轮细化）读取并输出历史消息。
- **无副作用**：不提交位点、不改变任何 Consumer Group 的消费进度。
- 不属于 MVP 的能力：改写/重置 group 已提交位点（如后续需要，另行作为独立功能讨论）。

**R13｜Consumer Group 仅绑定单个 Topic（第 13 轮确认）**
- 一个 Consumer Group 只消费一个 Topic；成员管理、分区分配、位点存储均以该 Topic 为范围。
- 已提交位点的键为 (group, topic, partition)（topic 维度保留但 MVP 内恒为绑定 topic）。
- 跨 Topic 的聚合消费需要分别使用不同的 group。

**R14｜Topic 分区数创建后不可修改（第 14 轮确认）**
- 分区数在创建 Topic 时确定，之后不支持增加或减少；上限 16 为每个 Topic 的创建上限。
- 同一 key 始终映射到同一分区，key 级别的分区归属永久稳定。
- 不提供扩容/重映射接口；需要更多分区时只能新建 Topic。

**R15｜CLI = 单二进制 + 子命令（第 15 轮确认）**
- 构建单一可执行文件，通过子命令区分角色与操作，例如：`broker`、`topic create|list`、`produce`、`consume`、`replay`（命令名与参数形式在 CLI 轮继续细化）。
- 源码内部仍按 Broker / Producer / Consumer / 公共协议分层，不因单二进制而耦合。
- 交付只需一个构建产物，部署与验收脚本共用同一入口。

**R16｜磁盘写满 = 主动检查空间 + 拒绝写入（第 16 轮确认，评审补充）**
- **返回 ack 之前，Broker 必须主动检查可用磁盘空间**（预留安全阈值）；空间不足时直接拒绝该写入，**不得仅依赖 `write()` 返回值**。
- 原因：R1 采用页缓存 ack，`ENOSPC` 可能滞后暴露；若仅依赖 `write()`，会出现"已 ack 但实际无法落盘"的窗口。
- 拒绝时返回明确错误（如"磁盘空间不足"），**不静默丢失**；已写入数据保持可读、可消费；Broker 进程保持运行，不因磁盘满而崩溃。
- Producer 收到该错误后按 R3 的有限重试策略处理，耗尽后明确失败退出。

**R17｜单条消息上限默认 1MB，可配置（第 17 轮确认）**
- 默认上限 1MB/条（含 key 与头信息），Broker 端可配置。
- **口径澄清**：该 1MB 指**存储记录**（存储头 + key + value）≤ 1 MiB；协议帧头与批量请求头不计入。
- 超限消息明确拒绝并返回错误，**不截断**。
- 该上限同时作为 Producer 批量请求中单条消息的约束。

**R18｜Consumer 默认持续跟随，可切换到读完即退（第 18 轮确认）**
- 默认行为：消费到当前末尾后阻塞等待新消息，用户 Ctrl+C 退出。
- 提供 `--exit-at-end`：读到当前末尾即退出，退出码 0，便于自动化验收脚本。
- 持续跟随模式下进程常驻；**MVP 内按启动时静态分配的分区消费**（R10），P1 再引入自动 rebalance。

**R19｜消息格式 = JSON Lines（第 19 轮确认）**
- Produce：从 stdin 或文件按行读入 JSON 对象（每行一条消息，含 key / value）；也支持命令行直接给出一条 JSON 消息。
- Consume / Replay：每行输出一条 JSON，至少包含 `partition`、`offset`、`key`、`value`；时间戳等附加字段可扩展。
- 输出为行分隔的 JSON（JSON Lines），便于脚本逐行解析与断言；消息中的换行等特殊字符由 JSON 转义承载。

**R20｜配置 = 命令行参数 + 默认值（第 20 轮确认）**
- 所有配置通过命令行参数提供，未指定则使用默认值；**不引入配置文件**。
- 默认值须固定并写入文档，验收脚本显式传参以保证可复现（配合 R9）。

**R21｜MVP 不增加 Topic 删除与组/位点查询（第 21 轮确认）**
- 不提供删除 Topic 的命令；创建时分区数选错，只能以新名字重建 Topic（与 R14 一致）。
- 不提供消费者组/已提交位点的查询命令；位点持久化通过"重启消费者观察是否重复消费"的行为验收。

**R22｜分区选择优先级：指定分区 > key 哈希 > 轮询（第 22 轮确认）**
- 显式指定分区时按指定分区写入；提供 key 时按哈希选分区；两者都没有时在可用分区间**轮询**。
- 无 key 的消息不保证跨分区的先后顺序；同一分区内仍严格保序（R2 不变）。
- 轮询使无 key 写入在分区之间均衡分布，避免单分区热点。

**R23｜批量发送 = 逐条返回结果（第 23 轮确认）**
- 批量发送时，Broker 对批次内每条消息分别返回结果：成功条目包含其 offset，失败条目包含失败原因或可定位标识。
- Producer 只重发失败的条目，不重发已成功的条目；逐条结果的协议细节属于设计阶段。
- 逐条重试与 R2 严格保序的协调方式见 R24。

**R24｜失败条目采用分区级阻塞重试（第 24 轮确认）**
- 某分区出现失败条目时，暂停向该分区发送后续消息；先重试失败条目，成功后再继续发送该分区的后续消息。
- 其他分区不受影响，可继续发送。
- 失败条目按 R3 重试耗尽后，Producer 明确失败退出（该分区自然停止），R2 的"发送顺序 = 写入顺序"始终成立。

**R25｜MVP 排除项全部确认（第 25 轮确认）**
- 不纳入：消息保留期清理、分区副本/Raft、ACL 安全、Web 管理界面。
- 交付形态：单机 Broker + 命令行工具（R15）；数据只增不删，磁盘写满按 R16 处理。

**R26｜吞吐负载口径 = payload 100B + key 8B（第 26 轮确认）**
- 验收消息固定为 payload 100 字节、key 8 字节；协议头不计入该 100B。
- 负载固定、可复现，作为 R5 吞吐验收与 R4 延迟验收的统一输入。

**R27｜offset 定义与重启重建（评审新增）**
- offset 是**分区内单调递增的逻辑序号**，与物理字节位置解耦；已写入消息的 offset 不因重启而改变。
- 重启时通过**扫描分段文件尾部**重建"下一条可用 offset"，重建依据与 R7 的记录完整性判据一致。
- 同一分区内 offset 严格递增、无空洞、不复用（丢弃的残缺尾部记录不占用 offset）。

**R28｜位点文件与消息采用同一可靠性口径（评审新增）**
- 消费者提交的位点文件采用与消息相同的可靠性口径（页缓存持久化；进程崩溃不丢，掉电按 R1 的边界处理）。
- 位点文件带**完整性校验**；检测到损坏时**回退到上一份完整位点**，不得导致 Broker 无法启动或全部位点丢失。
- 位点回退可能造成重复消费，仍满足至少一次语义（R3/R6）。

**R29｜批量失败退出前输出对账信息（评审新增）**
- 批量生产时，某分区重试耗尽导致 Producer 整体退出前，必须输出**已成功条目的 offset 汇总（按分区）**，供调用方对账与补发。
- 汇总覆盖本次批次内已成功写入的条目；具体输出形式在 CLI 细化时确定，但不得省略该能力。

**R30｜Topic 元数据必须持久化（评审补充）**
- 创建 Topic 时持久化其名称与分区数；Broker 启动时扫描重建 Topic 元数据。
- 单个 Topic 的元数据损坏时，**跳过该 Topic 并向 stderr 告警**，**不得阻止 Broker 启动**；其他 Topic 正常服务。
- 元数据的具体存储方式、完整性校验与损坏恢复方式在存储设计阶段（04）确定。

**R31｜Group 名目录安全规则（必要补充）**
- Consumer Group 名仅允许小写字母、数字、`-`、`_`，长度 1–64，与 Topic 名 Q-P8 完全一致。
- 不得包含 `/`、`..` 或空名；用于目录映射/CLI 校验时不得直接拼接未校验输入。
- 非法 Group 名明确拒绝并返回错误（具体错误码在 05 协议设计定义）。

## 6. 技术与平台约束

- 语言标准：**C++11/14**。
- 运行平台：**仅 Linux**。
- 构建系统：**CMake**。
- **禁止引入 boost、gRPC，以及任何现成的网络库或消息队列库**；网络通信与协议由项目自行实现（具体实现方式属设计阶段，不在需求阶段展开）。
- 压测工具必须用 **C++** 实现（R9）。

## 7. 术语表

| 术语 | 含义 |
| --- | --- |
| Broker | 消息队列服务端进程，负责存储、读写与位点管理 |
| Topic | 消息的逻辑分类，创建时确定分区数（≤16，不可修改） |
| Partition | Topic 内的并行与有序单元；分区内严格保序 |
| Offset | 分区内单调递增的逻辑序号（R27） |
| Commit Log | 按写入顺序追加的消息日志 |
| Segment | Commit Log 的分段文件 |
| Consumer Group | 消费者组；MVP 内绑定单个 Topic，一个分区同一时刻只分配给一个消费者 |
| 位点（Committed Offset） | 消费者组已提交的消费进度 |
| 自动提交 | 定时将"已处理位点"持久化（R6） |
| Rebalance | 组内分区重新分配；MVP 不做，P1（v1.1）可选（R10） |
| ack | Broker 对写入请求的确认；语义见 R1 |
| 至少一次 | 不丢消息、允许重复消费的投递语义 |
| 重放（Replay） | 按 offset 只读回放历史消息，不改变消费进度（R12） |
| JSON Lines | 每行一个 JSON 对象的文本格式（R19） |
| P99 | 99 分位延迟指标（R4） |
| 吞吐 | 单位时间写入消息数，按 Broker 总入口统计（R5） |

## 8. 验收矩阵

> MVP 验收以 V1、V2、V4–V11 为准；V3 为 P1（v1.1）验收项，不计入 MVP 门禁。

| 编号 | 验收项 | 操作步骤 | 通过标准 | 对应 R |
| --- | --- | --- | --- | --- |
| V1 | 进程崩溃恢复 | 多 Producer 写入并记录 ack 结果；对 Broker `kill -9`；直接重启 Broker；读取/回放已 ack 消息 | 重启无需人工干预；所有已 ack 消息可读且分区内顺序不变；offset 连续无空洞；未 ack 的残缺尾部被丢弃 | R1、R7、R27 |
| V2 | 位点重启续消费 | 消费者组消费一段并提交；对消费者 `kill -9`；以同 group、同 topic 重启 | 从最后已提交位点继续；不丢消息；重复不超过一个自动提交间隔内已处理的消息 | R6、R11、R28 |
| V3 | 动态 rebalance 接管（P1） | 同组启动多个消费者；`kill -9` 其中一个；观察分区归属 | 存活成员接管失效成员的分区并继续消费；同一分区不出现双消费者；本项为 v1.1 可选验收 | R10（P1） |
| V4 | 吞吐压测 | 固定基准机；多 Producer 并发、跨多分区、纯写；payload 100B + key 8B；固定脚本与参数运行 | Broker 总入口 ≥ 10 万条/秒；记录实测值与配置；未达标如实记录差距 | R5、R9、R26 |
| V5 | ack 延迟 | 同一基准机上发送单条/批量消息，统计 send → ack 延迟 | P99 < 10ms；记录实测值 | R4、R9 |
| V6 | 磁盘满 | 将数据盘填至阈值/限制可用空间；发起写入；读取已有数据；释放空间后再写入 | ack 前空间检查生效；新写入被拒绝且错误明确；已有数据可读；Broker 不崩溃；释放空间后恢复写入 | R16、R1 |
| V7 | 单条消息超限 | 发送大于 1MB 的单条消息 | 明确拒绝并返回错误；不截断、不静默；Broker 保持运行 | R17 |
| V8 | 批量失败 | 构造批内部分失败（如超限/空间不足）；观察逐条结果与重试；持续失败至耗尽 | 逐条结果正确；仅重发失败条目；同分区后续消息被阻塞至该条目成功或退出；退出前输出成功条目 offset 汇总；退出码非 0 | R23、R24、R29、R3 |
| V9 | 静态分区分配（MVP） | 同组启动两个消费者；观察各自分区；`kill -9` 其中一个 | 启动时分区分配互不重叠；失效消费者的分区暂停消费，不自动转移（MVP）；P1 行为另按 V3 验收 | R10（MVP） |
| V10 | 重放只读 | 消费者组推进位点；执行 replay 指定 offset 回放；再次启动消费者 | replay 正常输出历史消息；group 后续消费仍从原位点继续，不被 replay 改变 | R12、R11 |
| V11 | 分区内顺序 | 同一 key 连续发送多条消息；消费或回放检查顺序 | 同一分区内 offset 严格递增，消费顺序与写入顺序一致 | R2、R22 |
