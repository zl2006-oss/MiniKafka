## 2. 04 存储设计 → `docs/design/04.存储设计.md`

严格遵守 `docs/rules/storage-rules.md` 全部规约（CRC32 IEEE 且覆盖 total_len、256 MiB 分段 / 下限 2 MiB、稀疏索引 4 KiB 且为派生数据、位点双槽 generation+CRC+5s 全量快照、每 Topic 一个 meta 原子写、Topic/Group 名 `[a-z0-9_-]{1,64}`、record_size ≤ 1 MiB 且协议头不计入、不存时间戳、历史分段不可删改、封存分段只读、只截断 active segment）。

必须包含：
1. 数据目录总览（目录树 + R30 元数据 / 分段与索引 / Group 位点双槽的位置；与 03 第 7.2 节一致；标明 R31 Group 名校验在目录创建时何处执行）。
2. 消息记录格式逐字段表 + `total_len` 与 CRC 字节范围示意，说明 `record_size = 4 + total_len` 自洽关系；1 MiB 的两次校验点（协议请求校验、Storage Worker 追加前）；UTF-8 key/value 编码与 KEY_PRESENT 标志。
3. 分段文件与索引：命名（base offset 20 位十进制）、滚动触发、256 MiB 默认与 2 MiB 下限、索引条目结构与检查点时机、崩溃后从日志重建索引的步骤。
4. offset 与保序：分配规则（R2/R27）、分区亲和 Storage Worker 单分区串行、重启扫描 active segment 尾部重建 next_offset 的步骤。
5. 位点文件（R28）：格式、CRC 范围、写入时机（R6 已处理 / Q-P4 5s / Q-P6 正常退出补提交）、双槽切换流程，以及**四种崩溃时序**预期行为：tmp 写入中、tmp 写完未 rename、rename 后旧槽仍为旧 generation、两槽均损坏。
6. Topic 元数据（R30）：格式、原子写、启动扫描重建、单个损坏跳过且告警（含 topic 名与缺失路径）、与 AD-15 不可变快照的并发可见性。
7. 恢复流程（R1/R7/R16/R27）：启动到 acceptor 就绪顺序（AD-16）；`空间预检 → 分配 offset → 追加 → 页缓存写入成功 → 返回成功 → ack` 调用链，明确 fsync 不在链路；**预检通过但写失败的兜底（RK-06）**；低空间状态恢复。附**边界用例表**：空分段、半条记录、最后一条 CRC 损坏、跨分段基址不连续、封存分段损坏、元数据损坏、元数据存在但日志缺失、位点单槽/双槽损坏、残留 .tmp、磁盘写满中途崩溃，逐条给出预期行为与对应验收项。
8. 与 03 落点核对：Storage Worker 调用顺序、R23 批量逐条结果在存储层如何产生、AD-14 首个失败后停止该分区后续追加。
9. V1、V2、V6、V7、V8、V10、V11 由存储层哪些能力支撑，逐条映射。
10. 移交 05 的内容清单与移交 06 的一致性检查点。
